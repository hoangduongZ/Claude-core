01

Vòng lặp: model nghĩ, máy bạn làm

câu hỏi ngây thơ
Claude Code là app, service, hay cái gì đang chạy ngầm?
ẩn dụ

Không phải app. Hãy nghĩ như một đồng nghiệp bạn mời ngồi vào chính máy bạn, dùng chính tài khoản Windows của bạn. Anh ta không có chìa khoá riêng — đi lại được đúng những chỗ bạn đi lại được. Cái duy nhất giới hạn anh ta là tờ nội quy dán trên bàn: .claude\.

Một lượt trả lời đi qua bốn chặng
Chặng 3 là chỗ khác biệt lớn nhất so với chat trên web: tool chạy trên ổ đĩa của bạn, không phải trên server. Đóng terminal là tiến trình chết — không có daemon nào ở lại.

02

Git Bash — cây cầu duy nhất

câu hỏi ngây thơ
Tại sao một công cụ chạy trên Windows lại bắt tôi cài Git for Windows?
ẩn dụ

Claude được huấn luyện để nói tiếng Bash. Muốn chạy test, nó nghĩ ra câu có | và tail. Windows nghe không hiểu. Git for Windows mang theo một người phiên dịch tên Git Bash. Không có phiên dịch thì Claude vẫn nói, máy vẫn im.

Bấm để gỡ cầu và xem chuyện gì xảy ra
$ php artisan test → Tests: 42 passed
Khi cầu gãy, Claude không báo lỗi rõ ràng — nó chỉ thấy lệnh thất bại rồi thử cách khác, rồi lại thử, và bạn đốt token cho một vấn đề môi trường.
PowerShell — set một lần
# kiểm tra Git Bash
Test-Path "C:\Program Files\Git\bin\bash.exe"

# set vĩnh viễn (phải mở terminal MỚI)
setx CLAUDE_CODE_GIT_BASH_PATH "C:\Program Files\Git\bin\bash.exe"

Git Bash không chỉ ảnh hưởng tool Bash. Nó lan sang ba chỗ ở các mục sau: hooks (mục 7, mọi ví dụ trong docs đều viết bằng bash với jq), slash command có nhúng lệnh (mục 6), và MCP server chạy bằng npx (mục 9).

bẫy

Bạn viết trong CLAUDE.md rằng test chạy bằng php artisan test — máy bạn ngon. Đồng nghiệp cài Git ở D:\Tools\Git và không set biến môi trường thì mọi lệnh Bash đều fail. Điều kiện môi trường thuộc về checklist onboarding, không thuộc về CLAUDE.md.

tự kiểm tra

Chuyển hẳn sang WSL2 thì mục này còn đúng không? — Không. Trong WSL đã có bash thật. Đổi lại repo phải nằm trong filesystem WSL (~/work/…), để ở /mnt/c/… thì I/O chậm thấy rõ.

03

Ba tầng thư mục, không phải hai

câu hỏi ngây thơ
Có .claude ở home, lại có một cái nữa trong repo. Sao phải hai chỗ?
ẩn dụ

Giống nội quy công ty. Có quy định tập đoàn (IT dán, bạn không gỡ được), có thói quen cá nhân áp cho mọi dự án, và có quy ước riêng của từng dự án. Ba tầng, ba người chủ, và khi mâu thuẫn thì có thứ tự rõ ràng.

Bấm vào bất kỳ dòng nào để xem nó là gì
Màu vạch trái = ai sở hữu tầng đó. Xanh đậm là máy (IT), xanh vừa là bạn, xanh nhạt là repo/team.
bẫy

.claude.json ở home (dấu chấm, không có thư mục) và .claude\settings.json là hai thứ khác nhau. File đầu là state ứng dụng và phình rất nhanh; file sau mới là config bạn nên sửa tay. Sửa nhầm file đầu là cách nhanh nhất để mất session history.

tự kiểm tra

Muốn cả team bị chặn php artisan migrate:fresh. Viết vào đâu? — <repo>\.claude\settings.json, mục permissions.deny, rồi commit. Viết vào settings.local.json chỉ mình bạn bị chặn; viết vào ~\.claude\settings.json thì bạn bị chặn ở mọi repo kể cả repo không có Laravel.

04

Tầng nào thắng — bộ giải

câu hỏi ngây thơ
Cùng repo, sao máy tôi Claude tự sửa file luôn còn máy đồng nghiệp thì nó hỏi từng lần?
ẩn dụ

settings.json hoạt động như CSS specificity: càng cụ thể càng thắng, cái thua bị vứt hẳn. Đây là nguồn của gần hết những bug “máy tôi chạy khác máy anh”.

Bật/tắt từng file rồi xem giá trị nào thắng
Khoá đang giải: permissions.defaultMode. Bấm nút bên phải mỗi dòng để giả lập “file này có định nghĩa khoá đó”.

Trả lời câu hỏi ngây thơ: gần như chắc chắn máy bạn có <repo>\.claude\settings.local.json đặt defaultMode: "acceptEdits" — bạn tự thêm hôm nào đó rồi quên. File đó không vào git nên đồng nghiệp rơi về settings.json của team.

tự kiểm tra

Thêm rule vào ~\.claude\settings.json mà không có tác dụng. Kiểm tra theo thứ tự nào? — Từ trên xuống trong hình: managed policy → tham số dòng lệnh → settings.local.json → settings.json của team. Cái đầu tiên định nghĩa khoá đó chính là cái đang thắng. Dùng /config để xem kết quả thật sau khi merge.

05

Đè lên nhau vs cộng dồn

câu hỏi ngây thơ
CLAUDE.md cũng có ở hai tầng. Nó cũng đè nhau như settings chứ gì?

Không. Hai file trong .claude\ hợp nhất theo hai luật hoàn toàn khác nhau, và nhầm chỗ này là nguồn của rất nhiều hiểu lầm.

Hai luật hợp nhất, đặt cạnh nhau
Bên trái vứt bớt nên an toàn. Bên phải giữ hết nên hai file có thể mâu thuẫn mà không ai thắng — Claude phải tự đoán.
  • Đi ngược lên cây thư mục. Claude tìm CLAUDE.md từ thư mục hiện tại lên tới root — hữu ích cho monorepo.
  • Nạp lazy ở thư mục con. Khi đọc file trong app/Services/, nếu ở đó có CLAUDE.md thì mới nạp thêm.
  • Import bằng @. @docs/coding-standard.md nhúng file khác vào. Lồng nhau tối đa 5 cấp (verify). Import được cả từ home.
  • Lệnh. /init sinh CLAUDE.md; /memory mở để sửa; gõ # đầu dòng để thêm nhanh.

tự kiểm tra

Quy tắc “dùng CarbonImmutable” nên ở CLAUDE.md của repo hay của user? — Của repo. Đó là sự thật về codebase, không phải sở thích của bạn. Phép thử: nếu đồng nghiệp cũng cần biết thì nó thuộc về repo và phải vào git.

06

Bốn cơ chế — bản đồ hai trục

câu hỏi ngây thơ
Slash command, skill, subagent, hook — đều là file .md trong .claude\. Khác nhau chỗ nào?
ẩn dụ

Đừng phân biệt bằng định dạng file. Phân biệt bằng ai bấm nút và bên trong là prompt hay là code. Hai câu hỏi đó cho bạn một mặt phẳng, và bốn cơ chế rơi vào bốn góc khác nhau.

Bấm vào từng chấm
Càng đi lên trên và sang phải, bạn càng có đảm bảo chắc chắn hơn nhưng mất đi sự linh hoạt. Càng xuống dưới bên trái thì ngược lại.
.claude\commands\review-jp.mdgọi bằng /review-jp OrderService
---
description: Review code theo checklist bàn giao client Nhật
argument-hint: [tên class hoặc đường dẫn]
allowed-tools: Read, Grep, Bash(git diff:*)
model: claude-opus-5
---

Review $1 theo đúng thứ tự sau, không bỏ bước:

1. Diff hiện tại:  !`git diff --stat`
2. Checklist công ty:  @docs/review-checklist-jp.md
3. Mỗi phát hiện ghi rõ: severity / file:line / cách sửa
4. Kết luận phải là APPROVED hoặc CHANGES_REQUESTED

$1, $2 là tham số theo vị trí, $ARGUMENTS lấy tất cả. Dấu ! + backtick chạy shell và chèn output. Dấu @ nhúng file. Thư mục con tạo namespace: commands\jp\review.md → /jp:review.

bẫy

Đoạn !`git diff --stat` chạy qua Bash tool, tức là qua Git Bash (mục 2). Viết !`Get-ChildItem` vì tưởng mình đang ở PowerShell thì fail.

tự kiểm tra

Muốn chắc chắn mỗi lần Claude sửa file PHP thì Pint chạy format lại. Dùng cái nào? — Hook. Ba cái còn lại đều phụ thuộc model có nhớ làm hay không. Khi yêu cầu là “chắc chắn”, câu trả lời gần như luôn là hook.

07

Hooks — dòng thời gian một phiên

câu hỏi ngây thơ
Tôi copy ví dụ hook trong docs vào settings.json, không lỗi mà cũng không chạy.
ẩn dụ

Hook là công tắc hành trình trên dây chuyền: đến đúng vị trí thì bật, không cần ai ra lệnh. Vấn đề là công tắc trong tài liệu được đấu theo điện Linux. Cắm vào ổ Windows thì không nổ, nhưng cũng không chạy.

Bấm vào từng điểm trên dòng thời gian
Chỉ PreToolUse và UserPromptSubmit chặn được. Các event còn lại chỉ quan sát và phản ứng.

Giao thức: stdin JSON vào, exit code ra

  • exit 0 — cho qua.
  • exit 2 — chặn. stderr được đưa lại cho Claude như lời giải thích.
  • exit khác — lỗi, nhưng không chặn.
  • Hoặc in JSON ra stdout với decision / reason để kiểm soát tinh hơn.
.claude\hooks\gate-merge.ps1tên field payload cần verify
# Chặn git merge nếu chưa có code review APPROVED
$payload = [Console]::In.ReadToEnd() | ConvertFrom-Json
$cmd     = $payload.tool_input.command

if ($cmd -match 'git\s+merge') {
  $report = "docs/code-review-report.md"
  $ok = (Test-Path $report) -and
        (Select-String -Path $report -Pattern 'APPROVED' -Quiet)
  if (-not $ok) {
    [Console]::Error.WriteLine("Chua co code review APPROVED. Chay /review truoc.")
    exit 2        # 2 = chặn tool call
  }
}
exit 0
<repo>\.claude\settings.jsonđăng ký hook
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "powershell -NoProfile -ExecutionPolicy Bypass -File .claude/hooks/gate-merge.ps1",
        "timeout": 10
      }]
    }]
  }
}
bẫy — chỗ cần verify nhất tài liệu này

Tôi không chắc shell nào thực thi trường command trên native Windows (cmd.exe hay bash). An toàn nhất là gọi tường minh powershell -NoProfile -File … hoặc cmd /c …. Và test bằng hook echo vô hại trước — hook chặn mà hỏng thì khoá luôn tool, rất mất thời gian tìm.

bẫy — bảo mật

Hook chạy mã tuỳ ý với đúng quyền và credentials của bạn, tự động, không hỏi. Một hook trong repo bạn vừa clone là lỗ hổng thật. Đọc .claude\settings.json của repo lạ trước khi mở bằng Claude Code.

tự kiểm tra

Hook PostToolUse chạy Pint bị fail (exit 1). Claude có bị chặn không? — Không. Chỉ exit 2 mới chặn, và PostToolUse thì tool đã chạy xong rồi. Muốn ngăn từ đầu phải dùng PreToolUse.

08

Quyền — máy mô phỏng

câu hỏi ngây thơ
Claude có thể xoá nhầm file ngoài project của tôi không?
ẩn dụ

Mặc định Claude làm việc trong phòng là thư mục hiện tại và phải xin phép mỗi lần ra ngoài hoặc dùng dụng cụ nguy hiểm. Nhưng đây là văn phòng thật: không có nút reset, cái đã xoá phải lấy lại từ git.

<repo>\.claude\settings.jsonbộ rule dùng cho máy mô phỏng bên dưới
{
  "permissions": {
    "allow": [ "Bash(php artisan test:*)", "Bash(./vendor/bin/pint:*)",
               "Bash(composer install)", "Read(./**)" ],
    "deny":  [ "Bash(php artisan migrate:fresh:*)", "Bash(git push --force:*)",
               "Read(./.env)" ],
    "ask":   [ "Bash(git push:*)" ],
    "defaultMode": "default"
  }
}
Chọn một hành động, xem nó bị xử lý thế nào
Thứ tự giải: deny xét trước, rồi ask, rồi allow. Không khớp rule nào thì rơi về defaultMode.

Bốn chế độ

ModeHành viKhi nào dùng
defaultHỏi trước mỗi hành động có ảnh hưởngGiữ nguyên cho repo client.
acceptEditsTự sửa file, vẫn hỏi khi chạy lệnhRefactor nhiều file, khi git đang sạch.
planChỉ đọc, không ghi, không chạyCho Claude khảo sát và đề xuất trước.
bypassPermissionsKhông hỏi gì cảChỉ trong container/CI cô lập. Không bao giờ trên máy có repo client.
bẫy — viết path trên Windows

Trong JSON, \ là ký tự escape. Viết "Read(.\storage\**)" là sai; phải là "Read(./storage/**)" hoặc "Read(.\\storage\\**)". Tôi không chắc quy tắc khớp path trên Windows chuẩn hoá dấu gạch tới mức nào — test một rule trước khi phổ biến cho team, và ưu tiên dấu /.

tự kiểm tra

Thêm "Read(./.env)" vào deny có ngăn Claude chạy cat .env qua Bash không? — Không hiển nhiên. Read và Bash là hai tool khác nhau; chặn cái này không tự chặn cái kia. Muốn kín phải chặn cả pattern Bash tương ứng — hãy thử đúng mục đó trong máy mô phỏng ở trên.

09

MCP và cái bẫy cmd /c

câu hỏi ngây thơ
Tôi khai báo MCP y hệt bài hướng dẫn. Máy Mac của bạn tôi chạy, máy tôi thì không.
ẩn dụ

MCP server là thiết bị cắm thêm — cho Claude cửa vào Jira, database, Figma. Vấn đề rất vật lý: trên Windows, phích npx không cắm thẳng vào ổ được. Phải qua cục chuyển tên cmd /c.

Cùng một server, hai hệ điều hành
Đây là gotcha được ghi nhận rộng rãi, nhưng cú pháp chính xác nên verify lại với docs hiện hành.

Ba scope — chọn sai là lộ ra ngoài

ScopeGhi ở đâuAi thấy
localstate của bạn, theo từng projectChỉ bạn, chỉ project này. Mặc định.
project<repo>\.mcp.json — commit vào gitCả team, và cả khách khi bàn giao repo.
userconfig user của bạnChỉ bạn, nhưng ở mọi project.

Transport: stdio (process local), SSE và HTTP (server từ xa, có OAuth). Quản lý bằng claude mcp add / list / remove với cờ --scope, hoặc /mcp trong phiên. ${VAR} trong .mcp.json được expand từ biến môi trường — đó là cách commit file này mà không lộ token.

bẫy

.mcp.json vào git nghĩa là ai clone repo cũng được đề nghị chạy những server đó. Với repo có người ngoài đóng góp, đây là bề mặt tấn công. Đừng bật enableAllProjectMcpServers vô điều kiện ở tầng user.

tự kiểm tra

Cần MCP nội bộ công ty cho mọi repo, nhưng không muốn nó xuất hiện trong repo của khách. Scope nào? — user. Scope project ghi vào .mcp.json và đi theo repo tới tay khách.

10

Context đầy dần — chạy thử

câu hỏi ngây thơ
Làm việc một lúc thì Claude bắt đầu quên. Nó bị gì vậy?
ẩn dụ

Context là cái bàn làm việc có diện tích cố định. CLAUDE.md là tấm lót bàn — chiếm chỗ ngay từ đầu và không bao giờ dọn đi. Mỗi lượt trao đổi là thêm một tờ giấy. Bàn đầy thì có người đến gom hết giấy lại, viết tóm tắt vào một tờ, rồi vứt phần còn lại. Đó là auto-compact.

Session được index theo đường dẫn thư mục làm việc. Đổi tên thư mục repo là mất liên kết resume — file cũ vẫn còn nhưng --continue ở thư mục mới không thấy.

  • /context — xem đang dùng bao nhiêu. Nhìn cái này trước khi than “Claude quên”.
  • /compact — nén thủ công, giữ kết luận bỏ chi tiết.
  • /clear — xoá sạch. Rẻ hơn compact và thường đúng hơn khi bạn chuyển sang task khác hẳn.
  • /rewind — quay lại checkpoint, có thể khôi phục cả trạng thái code. Vị trí lưu không được document rõ.
bẫy

/compact làm mất chi tiết. Đang giữa một task cần chính xác (viết migration theo spec khách) mà compact thì Claude có thể quên một ràng buộc bạn dặn 40 lượt trước. Với việc quan trọng, ghi kết luận ra file trước khi compact — hoặc dùng hook PreCompact để tự động làm việc đó.

tự kiểm tra

Vì sao “ghi ra file” đáng tin hơn “để trong hội thoại”? — Vì context hữu hạn và bị nén định kỳ, còn file thì không. Đó chính là nguyên lý của pipeline ở mục 12: trạng thái sống trên disk, không sống trong đầu Claude.

Câu trả lời là “cả hai”, và ranh giới rất rõ: commit thứ mô tả dự án, ignore thứ mô tả cái máy của bạn. Thử tự phân loại trước khi xem đáp án.

bẫy

Repo bàn giao cho client Nhật thì .claude\ cũng đi theo. Hooks và commands trong đó là code sẽ chạy trên máy khách, còn CLAUDE.md là thứ khách sẽ đọc. Review chúng trong pull request đúng như review code — đừng để lọt ghi chú kiểu “chỗ này làm tạm cho kịp deadline”.

Muốn dùng acceptEdits cho riêng mình ở repo này, ghi vào đâu? — .claude\settings.local.json, và đảm bảo nó đã nằm trong .gitignore.

9 agent Digi Dinos — sơ đồ

câu hỏi ngây thơ
Pipeline 9 agent đang là 9 file SKILL.md. Chuyển sang máy host thì để đâu?

Đừng chuyển nguyên xi. Chín agent không cùng loại việc nên không nên cùng một cơ chế. Áp bản đồ hai trục ở mục 6 thì pipeline tự tách làm bốn nhóm.

Trái: agent · Phải: file .md sinh ra trên disk
Trạng thái truyền qua file .md trên disk, không qua context. Nhờ vậy pipeline chịu được việc bạn /clear giữa chừng, tắt máy, hay đổi người làm tiếp.

Cái được thêm khi lên máy host là ba thứ không có ở môi trường chat: agent chạm được vào code Laravel thật (chạy artisan test, đọc git diff), hook enforce được quy trình, và toàn bộ cấu hình đi vào git nên cả team dùng chung một phiên bản.

tự kiểm tra

Vì sao release-manager là hook chứ không phải subagent, dù nó cũng “làm việc”? — Vì yêu cầu thật của nó không phải “viết release note” mà là “không cho merge khi chưa APPROVED”. Ràng buộc phải chắc chắn thì phải nằm ngoài model. Phần viết release note đúng là subagent — nhưng đó là việc khác, tách ra.

13

Dump cấu trúc thật trên máy bạn

Bước cuối của Feynman: đối chiếu mô hình trong đầu với thực tế. Chạy lần lượt rồi so với các hình ở trên. Chỗ nào lệch thì thực tế đúng, tài liệu này sai.

PowerShell — chạy ở thư mục repo
# 1 — Claude bản nào, cài ở đâu
Get-Command claude | Format-List Source, Version
claude --version

# 2 — chẩn đoán PATH, Git Bash, quyền  (quan trọng nhất)
claude doctor

# 3 — cây tầng user, đối chiếu mục 3
tree /F "$env:USERPROFILE\.claude" | Select-Object -First 80

# 4 — settings user đang có key gì
Get-Content "$env:USERPROFILE\.claude\settings.json" -Raw

# 5 — .claude.json to cỡ nào
Get-Item "$env:USERPROFILE\.claude.json" | Select-Object Length, LastWriteTime

# 6 — bao nhiêu repo đang có transcript
Get-ChildItem "$env:USERPROFILE\.claude\projects" -Directory | Select-Object Name

# 7 — công ty đã set managed policy chưa
Test-Path "C:\ProgramData\ClaudeCode\managed-settings.json"

# 8 — Git Bash mà Claude sẽ dùng
$env:CLAUDE_CODE_GIT_BASH_PATH
Get-Command bash -ErrorAction SilentlyContinue | Select-Object Source

# 9 — tầng project
tree /F .\.claude

Trong phiên Claude Code, bốn lệnh đáng nhớ: /config xem cấu hình thật sau khi merge 5 tầng, /memory xem những CLAUDE.md nào đang nạp và theo thứ tự nào, /context xem context đầy bao nhiêu, /doctor chẩn đoán cài đặt.

tự kiểm tra

Nếu /config hiện một giá trị không có trong file nào ở mục 3 thì sao? — Hoặc là mặc định của Claude Code, hoặc đến từ managed policy (bạn có thể không có quyền đọc), hoặc từ tham số dòng lệnh nằm trong alias bạn dùng để khởi động.
