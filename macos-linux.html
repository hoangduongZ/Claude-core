Trên máy Unix, Claude thừa hưởng nguyên vẹn shell, PATH và quyền file của bạn. Đó vừa là sức mạnh vừa là toàn bộ danh sách bẫy.

Không cần cầu nối như trên Windows — bash có sẵn, mọi thứ chạy ngay. Đổi lại, những khác biệt tinh vi hơn sẽ cắn bạn: PATH khi shell không tương tác, BSD với GNU coreutils, và quyền thực thi trên file hook.

01

Vòng lặp: model nghĩ, máy bạn làm

câu hỏi ngây thơ
Claude Code là app, service, hay cái gì đang chạy ngầm?
ẩn dụ

Không phải app. Hãy nghĩ như một đồng nghiệp bạn mời ngồi vào chính máy bạn, đăng nhập bằng chính tài khoản của bạn. Anh ta không có uid riêng — đi lại được đúng những chỗ bạn đi lại được. Cái duy nhất giới hạn anh ta là tờ nội quy trong .claude/.

Một lượt trả lời đi qua bốn chặng
Chặng 3 là chỗ khác biệt lớn nhất so với chat trên web: tool chạy trên ổ đĩa của bạn với uid của bạn. Đóng terminal là tiến trình chết — không có daemon nào ở lại.

bẫy — sudo npm i -g

Đây là sai lầm phổ biến nhất trên Unix. Cài bằng sudo tạo ra file thuộc root trong thư mục global của npm. Sau đó auto-update chạy dưới uid của bạn và im lặng thất bại, hoặc tệ hơn là làm hỏng quyền của cả cây node_modules. Nếu lỡ làm rồi: gỡ sạch, đặt lại npm prefix về ~/.npm-global, rồi cài lại không sudo.

tự kiểm tra

Tắt máy giữa lúc Claude đang sửa file thì sao? — File vẫn nằm nguyên, đã sửa dở. Không transaction, không rollback tự động. Đó là lý do git và checkpoint (mục 10) quan trọng.

02

PATH — cái bẫy thay cho Git Bash

câu hỏi ngây thơ
Terminal của tôi chạy npx ngon lành. Sao Claude lại báo không tìm thấy?
ẩn dụ

Trên Windows vấn đề là không có shell. Trên Unix vấn đề ngược lại: có shell, nhưng không phải shell bạn quen. Cái ~/.zshrc nhồi đầy nvm, pyenv, Homebrew của bạn chỉ chạy khi bạn ngồi gõ. Tiến trình con sinh ra tự động thường nhận một PATH trần trụi hơn nhiều — như bước vào nhà mình nhưng đèn chưa bật.

Chọn cấu hình máy bạn, xem Claude thấy gì
Shell tương tác của bạn
đã nạp ~/.zshrc, ~/.bashrc
Tiến trình con Claude sinh ra
PATH tối giản, chưa nạp dotfiles
Đây là nguồn gốc của hầu hết lỗi “command not found” mà bạn thề là máy có cài. Cách chữa chắc chắn nhất: ghi đường dẫn tuyệt đối vào CLAUDE.md và vào cấu hình MCP, hoặc khai báo env.PATH trong settings.json.
~/.claude/settings.json — ghim PATH cho chắctự đổi theo máy bạn
{
  "env": {
    "PATH": "/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin"
  }
}
bẫy — Homebrew đổi chỗ trên Apple SiliconLinux: thiếu ~/.local/bin

Máy Intel cài Homebrew ở /usr/local/bin, máy Apple Silicon ở /opt/homebrew/bin. Nếu team bạn có cả hai loại máy, đừng hardcode một đường dẫn vào settings.json rồi commit — đồng nghiệp máy Intel sẽ mất sạch php, composer. Cấu hình PATH thuộc về settings.local.json, không thuộc về file share.

Nhiều distro không tự thêm ~/.local/bin vào PATH cho shell không phải login shell. Binary claude nằm đúng ở đó. Triệu chứng: chạy tay thì được, chạy trong script hay systemd unit thì claude: command not found.

tự kiểm tra

Vì sao ghi php artisan test vào CLAUDE.md lại rủi ro hơn ghi ./vendor/bin/phpunit? — Cái sau là đường dẫn tương đối tính từ repo, luôn giải được. Cái trước phụ thuộc php có trong PATH của tiến trình con hay không — thứ bạn không kiểm soát được từ file commit vào git.

03

Ba tầng thư mục, không phải hai

câu hỏi ngây thơ
Có .claude ở home, lại có một cái nữa trong repo. Sao phải hai chỗ?
ẩn dụ

Giống nội quy công ty. Có quy định tập đoàn (root dán, bạn không gỡ được), có thói quen cá nhân áp cho mọi dự án, và có quy ước riêng của từng dự án. Ba tầng, ba người chủ, và khi mâu thuẫn thì có thứ tự rõ ràng.

Bấm vào bất kỳ dòng nào để xem nó là gì
Màu vạch trái = ai sở hữu tầng đó. Xanh đậm là máy (root), xanh vừa là bạn, xanh nhạt là repo/team. Đổi nút macOS/Linux ở đầu trang để thấy tầng máy đổi chỗ.
bẫy — quyền file

Trên macOS, token đăng nhập được cất trong Keychain chứ không phải file thường — an toàn hơn, nhưng cũng nghĩa là copy nguyên thư mục ~/.claude sang máy khác sẽ không mang theo đăng nhập. Chi tiết cơ chế lưu trữ nên verify lại.

Trên Linux thường không có keychain, token nằm trong ~/.claude/.credentials.json dạng file thường. Kiểm tra quyền của nó ngay: phải là 600 và thuộc về bạn. Trên máy dùng chung hoặc server CI, đây là file đầu tiên cần nghĩ tới. Vị trí file là quan sát thực tế, không phải API ổn định.

tự kiểm tra

Muốn cả team bị chặn php artisan migrate:fresh. Viết vào đâu? — <repo>/.claude/settings.json, mục permissions.deny, rồi commit. Viết vào settings.local.json chỉ mình bạn bị chặn; viết vào ~/.claude/settings.json thì bạn bị chặn ở mọi repo.

04

Tầng nào thắng — bộ giải

câu hỏi ngây thơ
Cùng repo, sao máy tôi Claude tự sửa file luôn còn máy đồng nghiệp thì nó hỏi từng lần?
ẩn dụ

settings.json hoạt động như CSS specificity: càng cụ thể càng thắng, cái thua bị vứt hẳn. Đây là nguồn của gần hết những bug “máy tôi chạy khác máy anh”.

Bật/tắt từng file rồi xem giá trị nào thắng
Khoá đang giải: permissions.defaultMode. Bấm nút bên phải mỗi dòng để giả lập “file này có định nghĩa khoá đó”.

Trả lời câu hỏi ngây thơ: gần như chắc chắn máy bạn có <repo>/.claude/settings.local.json đặt defaultMode: "acceptEdits" — bạn tự thêm hôm nào đó rồi quên. File đó không vào git nên đồng nghiệp rơi về settings.json của team.

tự kiểm tra

Thêm rule vào ~/.claude/settings.json mà không có tác dụng. Kiểm tra theo thứ tự nào? — Từ trên xuống trong hình: managed policy → tham số dòng lệnh → settings.local.json → settings.json của team. Cái đầu tiên định nghĩa khoá đó chính là cái đang thắng. Dùng /config để xem kết quả thật sau khi merge.

05

Đè lên nhau vs cộng dồn

câu hỏi ngây thơ
CLAUDE.md cũng có ở hai tầng. Nó cũng đè nhau như settings chứ gì?

Không. Hai file trong .claude/ hợp nhất theo hai luật hoàn toàn khác nhau, và nhầm chỗ này là nguồn của rất nhiều hiểu lầm.

Hai luật hợp nhất, đặt cạnh nhau
Bên trái vứt bớt nên an toàn. Bên phải giữ hết nên hai file có thể mâu thuẫn mà không ai thắng — Claude phải tự đoán.
  • Đi ngược lên cây thư mục. Claude tìm CLAUDE.md từ thư mục hiện tại lên tới / — hữu ích cho monorepo.
  • Nạp lazy ở thư mục con. Khi đọc file trong app/Services/, nếu ở đó có CLAUDE.md thì mới nạp thêm.
  • Import bằng @. @docs/coding-standard.md nhúng file khác vào. Lồng nhau tối đa 5 cấp (verify). Import được cả từ ~/.
  • Lệnh. /init sinh CLAUDE.md; /memory mở để sửa; gõ # đầu dòng để thêm nhanh.

Quy tắc “dùng CarbonImmutable” nên ở CLAUDE.md của repo hay của user? — Của repo. Đó là sự thật về codebase, không phải sở thích của bạn. Phép thử: nếu đồng nghiệp cũng cần biết thì nó thuộc về repo và phải vào git.

06

Bốn cơ chế — bản đồ hai trục

câu hỏi ngây thơ
Slash command, skill, subagent, hook — đều là file .md trong .claude/. Khác nhau chỗ nào?
ẩn dụ

Đừng phân biệt bằng định dạng file. Phân biệt bằng ai bấm nút và bên trong là prompt hay là code. Hai câu hỏi đó cho bạn một mặt phẳng, và bốn cơ chế rơi vào bốn góc khác nhau.

Bấm vào từng chấm
Càng lên trên và sang phải, đảm bảo càng chắc nhưng mất linh hoạt. Càng xuống dưới bên trái thì ngược lại.
.claude/commands/review-jp.mdgọi bằng /review-jp OrderService
---
description: Review code theo checklist bàn giao client Nhật
argument-hint: [tên class hoặc đường dẫn]
allowed-tools: Read, Grep, Bash(git diff:*)
model: claude-opus-5
---

Review $1 theo đúng thứ tự sau, không bỏ bước:

1. Diff hiện tại:  !`git diff --stat`
2. Checklist công ty:  @docs/review-checklist-jp.md
3. Mỗi phát hiện ghi rõ: severity / file:line / cách sửa
4. Kết luận phải là APPROVED hoặc CHANGES_REQUESTED

$1, $2 là tham số theo vị trí, $ARGUMENTS lấy tất cả. Dấu ! + backtick chạy shell và chèn output. Dấu @ nhúng file. Thư mục con tạo namespace: commands/jp/review.md → /jp:review.

tự kiểm tra

Muốn chắc chắn mỗi lần Claude sửa file PHP thì Pint chạy format lại. Dùng cái nào? — Hook. Ba cái còn lại đều phụ thuộc model có nhớ làm hay không. Khi yêu cầu là “chắc chắn”, câu trả lời gần như luôn là hook.

07

Hooks — dòng thời gian một phiên

câu hỏi ngây thơ
Hook của tôi viết bằng bash, chạy tay thì ngon, mà Claude không thấy nó chạy gì cả.
ẩn dụ

Hook là công tắc hành trình trên dây chuyền: đến đúng vị trí thì bật, không cần ai ra lệnh. Trên Unix thì điện đã đúng chuẩn rồi — nhưng công tắc vẫn không bật nếu bạn quên cắm phích: chmod +x, shebang, và đường dẫn tuyệt đối.

Bấm vào từng điểm trên dòng thời gian
Chỉ PreToolUse và UserPromptSubmit chặn được. Các event còn lại chỉ quan sát và phản ứng.

Giao thức: stdin JSON vào, exit code ra

  • exit 0 — cho qua.
  • exit 2 — chặn. stderr được đưa lại cho Claude như lời giải thích.
  • exit khác — lỗi, nhưng không chặn.
  • Hoặc in JSON ra stdout với decision / reason để kiểm soát tinh hơn.
.claude/hooks/gate-merge.shtên field payload cần verify
#!/usr/bin/env bash
# Chặn git merge nếu chưa có code review APPROVED
set -euo pipefail

payload=$(cat)
cmd=$(printf '%s' "$payload" | jq -r '.tool_input.command // ""')

if [[ "$cmd" =~ git[[:space:]]+merge ]]; then
  report="docs/code-review-report.md"
  if [[ ! -f "$report" ]] || ! grep -q 'APPROVED' "$report"; then
    echo "Chua co code review APPROVED. Chay /review truoc." >&2
    exit 2      # 2 = chặn tool call
  fi
fi
exit 0
bắt buộc — không có bước này hook im lặng không chạy
chmod +x .claude/hooks/gate-merge.sh
# macOS chưa có jq: brew install jq
# Debian/Ubuntu:    sudo apt install jq
<repo>/.claude/settings.jsonđăng ký hook
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "$CLAUDE_PROJECT_DIR/.claude/hooks/gate-merge.sh",
        "timeout": 10
      }]
    }]
  }
}

Biến $CLAUDE_PROJECT_DIR giúp hook chạy đúng dù thư mục hiện tại là gì — nên verify tên biến này với docs hiện hành. Nếu không chắc, dùng đường dẫn tuyệt đối.

macOS không phải Linux: BSD vs GNU

Đây là khác biệt lớn nhất trong hai hệ này, và nó cắn đúng vào hook vì hook là chỗ bạn viết shell script thật.

ViệcmacOS (BSD)Linux (GNU)
Sửa file tại chỗsed -i '' 's/a/b/' fsed -i 's/a/b/' f
Regex Perlgrep -P không cógrep -P 'x(?=y)'

Nếu team có cả máy Mac và server Linux, hook viết cho bên này sẽ hỏng ở bên kia. Cách thoát: viết hook bằng PHP hoặc Python thay vì shell — bạn đã có sẵn PHP trong dự án Laravel rồi, và nó hành xử giống nhau trên cả hai hệ.

bẫy — bảo mật

Hook chạy mã tuỳ ý với đúng uid và credentials của bạn, tự động, không hỏi. Một hook trong repo bạn vừa clone là lỗ hổng thật. Đọc .claude/settings.json của repo lạ trước khi mở bằng Claude Code — trên Unix thì git clone xong chạy claude ngay là thói quen rất dễ hình thành.

tự kiểm tra

Hook PostToolUse chạy Pint bị fail (exit 1). Claude có bị chặn không? — Không. Chỉ exit 2 mới chặn, và PostToolUse thì tool đã chạy xong rồi. Muốn ngăn từ đầu phải dùng PreToolUse.

08

Quyền — máy mô phỏng

câu hỏi ngây thơ
Claude có thể xoá nhầm file ngoài project của tôi không?
ẩn dụ

Mặc định Claude làm việc trong phòng là thư mục hiện tại và phải xin phép mỗi lần ra ngoài hoặc dùng dụng cụ nguy hiểm. Nhưng đây là văn phòng thật: không có nút reset, cái đã xoá phải lấy lại từ git.

<repo>/.claude/settings.jsonbộ rule dùng cho máy mô phỏng bên dưới
{
  "permissions": {
    "allow": [ "Bash(./vendor/bin/phpunit:*)", "Bash(./vendor/bin/pint:*)",
               "Bash(composer install)", "Read(./**)" ],
    "deny":  [ "Bash(php artisan migrate:fresh:*)", "Bash(git push --force:*)",
               "Bash(rm -rf:*)", "Read(./.env)" ],
    "ask":   [ "Bash(git push:*)" ],
    "defaultMode": "default"
  }
}
Chọn một hành động, xem nó bị xử lý thế nào
Thứ tự giải: deny xét trước, rồi ask, rồi allow. Không khớp rule nào thì rơi về defaultMode.

Bốn chế độ

ModeHành viKhi nào dùng
defaultHỏi trước mỗi hành động có ảnh hưởngGiữ nguyên cho repo client.
acceptEditsTự sửa file, vẫn hỏi khi chạy lệnhRefactor nhiều file, khi git đang sạch.
planChỉ đọc, không ghi, không chạyCho Claude khảo sát và đề xuất trước.
bypassPermissionsKhông hỏi gì cảChỉ trong container cô lập. Trên máy dev có SSH key và token thì không bao giờ.

macOS còn một lớp nữa: TCC

Hệ điều hành có lớp quyền riêng nằm ngoài Claude Code. Tiến trình claude thừa hưởng quyền của ứng dụng terminal đang chạy nó — Terminal.app, iTerm2, hay VS Code. Nếu app đó chưa được cấp quyền vào ~/Documents, ~/Desktop, hay Full Disk Access, thì Claude đọc file ở đó sẽ fail dù permission rule của bạn cho phép.

Triệu chứng dễ nhận: Operation not permitted trên một thư mục mà ls trong Finder thấy bình thường. Chỗ sửa: System Settings → Privacy & Security → Files and Folders (hoặc Full Disk Access), cấp cho terminal chứ không phải cho claude.

Linux: quyền là quyền POSIX, không có lớp nào khác

Không có TCC. Cái chặn bạn chỉ có ba thứ: uid/gid và mode bit, SELinux hoặc AppArmor nếu distro bật, và namespace nếu bạn chạy trong container. Đơn giản hơn macOS, nhưng cũng nghĩa là không có lưới an toàn nào ngoài permission rule của chính Claude Code.

Trên server dùng chung hoặc CI: chạy Claude Code dưới một user riêng, chỉ có quyền vào đúng cây repo. Đó là cách cô lập rẻ và chắc nhất, chắc hơn mọi cấu hình trong settings.json.

Claude Code có tính năng sandbox cho bash. Trên Unix nền tảng sẵn có tốt hơn Windows — macOS có Seatbelt, Linux có namespace và seccomp — nhưng mức độ Claude Code thật sự dùng tới đâu là chỗ bạn cần verify với docs, đừng coi nó là lớp bảo vệ chính.

tự kiểm tra

Thêm "Read(./.env)" vào deny có ngăn Claude chạy cat .env qua Bash không? — Không hiển nhiên. Read và Bash là hai tool khác nhau; chặn cái này không tự chặn cái kia. Hãy thử đúng mục đó trong máy mô phỏng ở trên.

MCP và cái bẫy npx không thấy

câu hỏi ngây thơ
MCP server của tôi báo lỗi khởi động, mà gõ npx trong terminal thì chạy ngay.
ẩn dụ

Trên Windows, phích npx không cắm thẳng vào ổ được nên phải qua cục chuyển cmd /c. Trên Unix phích cắm vừa — nhưng ổ điện lại ở phòng khác. Đây chính là mục 2 quay lại: tiến trình MCP sinh ra không có PATH đã nạp nvm của bạn.

Cùng một server, hai cách khai báo
MCP server "filesystem" failed to start: spawn npx ENOENT
Trên Windows lỗi này hiện ra rõ ràng vì ai cũng biết phải thêm cmd /c. Trên Unix nó ẩn hơn nhiều, vì bạn thấy npx chạy được nên không nghĩ tới PATH.
<repo>/.mcp.json — bản chắc chắn chạyverify cú pháp hiện hành
{
  "mcpServers": {
    "filesystem": {
      "command": "/Users/hoang/.nvm/versions/node/v20.11.0/bin/npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem",
               "/Users/hoang/work/ec-site-tanaka"],
      "env": { "SOME_TOKEN": "${SOME_TOKEN}" }
    }
  }
}
bẫy — đường dẫn tuyệt đối thì không commit được

Bạn vừa sửa được lỗi, nhưng /Users/hoang/… chỉ đúng trên máy bạn. Commit file này là đồng nghiệp hỏng ngay. Hai lối thoát: đặt server đó ở scope user thay vì project, hoặc dùng ${VAR} và để mỗi người tự khai biến môi trường. Đừng commit đường dẫn home của bạn vào repo của khách.

Ba scope

ScopeGhi ở đâuAi thấy
localstate của bạn, theo từng projectChỉ bạn, chỉ project này. Mặc định.
project<repo>/.mcp.json — commit vào gitCả team, và cả khách khi bàn giao repo.
userconfig user của bạnChỉ bạn, nhưng ở mọi project.

Transport: stdio (process local), SSE và HTTP (server từ xa, có OAuth). Quản lý bằng claude mcp add / list / remove với cờ --scope, hoặc /mcp trong phiên.

tự kiểm tra

Cần MCP nội bộ công ty cho mọi repo, nhưng không muốn nó xuất hiện trong repo của khách. Scope nào? — user. Scope project ghi vào .mcp.json và đi theo repo tới tay khách.

Context đầy dần — chạy thử

câu hỏi ngây thơ
Làm việc một lúc thì Claude bắt đầu quên. Nó bị gì vậy?
ẩn dụ

Context là cái bàn làm việc có diện tích cố định. CLAUDE.md là tấm lót bàn — chiếm chỗ ngay từ đầu và không bao giờ dọn đi. Mỗi lượt là thêm một tờ giấy. Bàn đầy thì có người gom hết giấy lại, viết tóm tắt vào một tờ, vứt phần còn lại. Đó là auto-compact.

Bấm để chạy một phiên làm việc
■ CLAUDE.md — trả tiền mỗi lượt ■ hội thoại + file đã đọc 6%
phiên mới · context 6%
Bấm “CLAUDE.md 4000 dòng” rồi chạy lại: số lượt trước khi compact giảm rõ rệt. Đó là cái giá thật của việc nhét tài liệu thiết kế vào memory.
~/.claude/projects/format nội bộ
projects/
├── -Users-hoang-work-ec-site-tanaka/   # tên = đường dẫn repo đã encode
│   ├── 1f4c8e2a-….jsonl              # một phiên = một file
│   └── 9b0d3311-….jsonl
└── -Users-hoang-work-crm-sato/

Session được index theo đường dẫn thư mục làm việc. Đổi tên thư mục repo, hoặc mở repo qua một symlink khác, là mất liên kết resume — file cũ vẫn còn nhưng --continue ở đường dẫn mới không thấy.

  • /context — xem đang dùng bao nhiêu. Nhìn cái này trước khi than “Claude quên”.
  • /compact — nén thủ công, giữ kết luận bỏ chi tiết.
  • /clear — xoá sạch. Rẻ hơn compact và thường đúng hơn khi chuyển task khác hẳn.
  • /rewind — quay lại checkpoint, có thể khôi phục cả trạng thái code. Vị trí lưu không được document rõ.
bẫy

/compact làm mất chi tiết. Đang giữa một task cần chính xác mà compact thì Claude có thể quên một ràng buộc bạn dặn 40 lượt trước. Với việc quan trọng, ghi kết luận ra file trước khi compact — hoặc dùng hook PreCompact để tự động làm việc đó.

tự kiểm tra

Vì sao “ghi ra file” đáng tin hơn “để trong hội thoại”? — Vì context hữu hạn và bị nén định kỳ, còn file thì không. Đó chính là nguyên lý của pipeline ở mục 12: trạng thái sống trên disk, không sống trong đầu Claude.

Commit hay ignore — tự chấm

câu hỏi ngây thơ
Thư mục .claude trong repo — nên commit hay ignore?

Câu trả lời là “cả hai”, và ranh giới rất rõ: commit thứ mô tả dự án, ignore thứ mô tả cái máy của bạn. Thử tự phân loại trước khi xem đáp án.

Chọn cho từng file rồi bấm chấm điểm
bẫy

Repo bàn giao cho client Nhật thì .claude/ cũng đi theo. Hooks và commands trong đó là code sẽ chạy trên máy khách, còn CLAUDE.md là thứ khách sẽ đọc. Review chúng trong pull request đúng như review code. Và nhớ: file hook mất bit +x khi qua một số cách đóng gói — git giữ được, nhưng zip hay copy qua Windows thì không.

9 agent Digi Dinos — sơ đồ

câu hỏi ngây thơ
Pipeline 9 agent đang là 9 file SKILL.md. Chuyển sang máy host thì để đâu?

Đừng chuyển nguyên xi. Chín agent không cùng loại việc nên không nên cùng một cơ chế. Áp bản đồ hai trục ở mục 6 thì pipeline tự tách làm bốn nhóm.

Trái: agent · Phải: file .md sinh ra trên disk
Trạng thái truyền qua file .md trên disk, không qua context. Nhờ vậy pipeline chịu được việc bạn /clear giữa chừng, tắt máy, hay đổi người làm tiếp.

Trên Unix, pipeline này còn mở ra một khả năng mà Windows khó làm gọn: chạy nhiều phiên song song bằng git worktree. Mỗi worktree là một thư mục riêng nên Claude Code coi là một project riêng, có session riêng, và bạn có thể để một agent viết code trong khi agent khác review nhánh trước đó.

chạy song song bằng worktree
git worktree add ../ec-site-feat-order feature/order
cd ../ec-site-feat-order && claude    # phiên riêng, context riêng
tự kiểm tra

Vì sao release-manager là hook chứ không phải subagent, dù nó cũng “làm việc”? — Vì yêu cầu thật của nó không phải “viết release note” mà là “không cho merge khi chưa APPROVED”. Ràng buộc phải chắc chắn thì phải nằm ngoài model. Phần viết release note đúng là subagent — nhưng đó là việc khác, tách ra.

Dump cấu trúc thật trên máy bạn

Bước cuối của Feynman: đối chiếu mô hình trong đầu với thực tế. Chạy lần lượt rồi so với các hình ở trên. Chỗ nào lệch thì thực tế đúng, tài liệu này sai.

zsh / bash — chạy ở thư mục repo
# 1 — Claude bản nào, cài ở đâu
which claude && claude --version

# 2 — chẩn đoán PATH, quyền, cài đặt  (quan trọng nhất)
claude doctor

# 3 — cây tầng user, đối chiếu mục 3
ls -la ~/.claude
find ~/.claude -maxdepth 2 | head -40

# 4 — settings user đang có key gì
cat ~/.claude/settings.json

# 5 — .claude.json to cỡ nào
ls -lh ~/.claude.json

# 6 — bao nhiêu repo đang có transcript
ls ~/.claude/projects

# 7 — công ty đã set managed policy chưa
ls -l '/Library/Application Support/ClaudeCode/managed-settings.json'

# 8 — PATH mà tiến trình con nhìn thấy  (mục 2)
env -i sh -c 'echo $PATH; command -v node npx php || echo THIEU'

# 9 — hook đã có bit thực thi chưa  (mục 7)
ls -l .claude/hooks/

# 10 — quyền file credentials
ls -l ~/.claude/.credentials.json 2>/dev/null || echo "khong co - co the dang dung keychain"

# 11 — tầng project
find .claude -maxdepth 2

Trong phiên Claude Code, bốn lệnh đáng nhớ: /config xem cấu hình thật sau khi merge 5 tầng, /memory xem những CLAUDE.md nào đang nạp và theo thứ tự nào, /context xem context đầy bao nhiêu, /doctor chẩn đoán cài đặt.

tự kiểm tra

Lệnh số 8 ở trên thật ra đang chứng minh điều gì? — env -i xoá sạch môi trường rồi chạy shell, mô phỏng đúng cảnh tiến trình con không nạp dotfiles. Nếu nó in ra THIEU thì bạn vừa tái hiện được nguyên nhân của mục 2 và mục 9 ngay trên máy mình.
